1. System Architecture Overview

Core engineering principles, technology stack, and layer separation

The Petty Cash & Expense Management System is designed as a modern, multi-tier enterprise platform leveraging **.NET MAUI Blazor Hybrid** for mobile cross-platform field usage and **ASP.NET Core Web API** for centralized business logic and financial custody.

💻
Shared Core Project
Contains Data Transfer Objects (DTOs: `CreateAdvanceDto`, `ExpenseDto`, `LoginRequestDto`), type-safe C# Enums (`AdvanceStatus`, `ExpenseStatus`, `SettlementType`), and service interface contracts (`ITransactionService`, `IAuthService`). Shared across Web & Mobile clients.
⚙️
Backend Server Project
Houses EF Core domain entity models (`User`, `AdvanceRequest`, `Expense`, `Receipt`, `Reconciliation`), `AppDbContext`, API Controllers, and concrete service implementations (`TransactionService`, `AuthService`) containing validation rules, SQL Server persistence, and audit logging.
📱
Client Applications
Responsive Blazor Web application for office management/approvers and .NET MAUI Blazor Hybrid app for budget Android/iOS mobile devices used by field officers.
🔒
Security & PB-RBAC
Permission-Based Role-Based Access Control. `SuperAdmin` is the single seeded system root role; all custom roles and granular permissions are managed dynamically.

5. Business Activity Workflows

Step-by-step procedural decision trees for all core financial operations

💡 Key Workflow & Diagram Architectural Notes

1. Input Validation Nodes: System validation checks ensure data integrity (e.g., requested amount > $0, mandatory purpose entered, active employee account) before saving or processing.

2. Single-Page Transaction Model: Expense items are added directly to an active advance on a unified transaction dashboard rather than being isolated standalone forms.

3. Tied Review & Decision Step: Reviewing, approving, and rejecting are unified into a single decision node: Approve (Set Status = Approved) or Reject (Record Rejection Reason & Set Status = Rejected).

4. Clear Reconciliation Terminology: Reconcile outcomes use explicit business terms: Unspent Cash Remaining (Employee Returns Cash), Out-of-Pocket Deficit (Company Reimburses), and Exact Balance Match ($0 Difference).

7.2 Endpoints Execution Matrix

Group HTTP & Route Description & Business Rules Scope & MVP
AuthAPI POST /api/auth/login Authenticates credentials with salted password hashing (NFR-d). Returns JWT session token. Logs audit event. In-Scope • Phase 1
UserAPI POST /api/users Admin provisions user accounts and assigns roles (FR-01). Enforces unique email constraint. In-Scope • Phase 1
AdvanceAPI POST /api/advances Employee creates advance request specifying amount (UGX), destination, and purpose (FR-02). Status = Pending. In-Scope • Phase 2
AdvanceAPI POST /api/advances/{id}/approve Approver grants request (BR-001). Sets approved amount. Triggers email notification to employee. In-Scope • Phase 2
AdvanceAPI POST /api/advances/{id}/issue-funds Custodian logs physical/electronic release of capital (FR-03). Status transitions to FundsIssued. In-Scope • Phase 2
AdvanceAPI POST /api/advances/{id}/additional Employee requests supplemental funds for active advance (FR-06, BR-005). Requires independent approval. In-Scope • Phase 2
ExpenseAPI POST /api/expenses Employee records field/office expense against active advance (FR-04, BR-003). Category must match 6 standard types. In-Scope • Phase 1
ReceiptAPI POST /api/expenses/{id}/receipt Uploads camera photo / PDF receipt (FR-05, BR-004). Applies client-side compression before storage. In-Scope • Phase 1
ExpenseAPI POST /api/expenses/{id}/resubmit Employee resubmits corrected rejected expense within strict 3-calendar-day window (Section 8 Policy). In-Scope • Phase 2
ReconciliationAPI GET /api/reconciliations/advance/{id}/calculate Computes balance ($\text{Total Issued} - \text{Total Spent}$). Evaluates Surplus vs Shortfall outcome (FR-09, BR-008). In-Scope • Phase 2
ReconciliationAPI POST /api/reconciliations/advance/{id}/finalize Custodian sign-off. Permanently locks advance and expenses into Immutable Read-Only state. In-Scope • Phase 2
ReportAPI GET /api/reports/export Generates 1-click downloadable CSV/Excel reports across 10 executive dimensions (FR-10). In-Scope • Phase 1/2

sequenceDiagram

    Auth->>DB: Query user record by email

        Auth->>DB: Update IsLockedOut = 1 & LockoutEnd = SYSDATETIME + 15 mins
        DB-->>Auth: Account locked
        Auth->>Audit: Log security alert: Account Locked Out
        Auth-->>API: Account locked out
        API-->>Client: HTTP 423 Locked ("Account locked due to excessive failed attempts. Try again in 15 minutes.")

        Deny["Deny Request (403 Forbidden)\nAudit Unauthorized Attempt"]

        Request --> Identity
        Identity --> SuperAdminCheck
        SuperAdminCheck -->|"YES (Root Bypass)"| Allow
        SuperAdminCheck -->|"NO (Standard User)"| PermissionCheck
        PermissionCheck -->|"YES (Permission Granted)"| Allow
        PermissionCheck -->|"NO (Permission Missing/Revoked)"| Deny
    end

    UserPermissions -.->|"Queried at Login for JWT Claims"| Identity

12. Service-Oriented Class Architecture & Project Layering

Clean Architecture separation: Shared DTOs/Interfaces vs. Server EF Entities & Business Services

📦

Shared Project

Shared across Web & Mobile Clients
  • Data Transfer Objects (DTOs): CreateAdvanceDto, ExpenseDto, LoginRequestDto, etc.
  • Service Interfaces: IAdvanceService, IExpenseService, IAuthService.
  • Type-Safe Enums: AdvanceStatus, ExpenseStatus, SettlementType.
⚙️

Backend Server Project

ASP.NET Core Web API + EF Core
  • EF Core Database Entities: User, AdvanceRequest, Expense, Reconciliation.
  • DbContext: AppDbContext managing migrations & SQL Server persistence.
  • Service Realizations: AdvanceService, ExpenseService, AuthService implementing Shared interfaces.
  • API Controllers: Lightweight HTTP endpoints routing requests to Services.

💡 Why Service-Oriented Class Architecture is Essential

1. What it is: Encapsulating all domain rules, validation, database queries, and workflow logic into dedicated C# Service classes (e.g., AdvanceService) rather than writing code inside API Controllers or Blazor UI components.

2. Why it is necessary:

  • Prevents Fat Controllers: API Controllers remain clean 5-line wrappers handling only HTTP status codes and route binding.
  • Code Reusability: Business rules can be called by Web API endpoints, background queue processors, or CLI tools without duplicating logic.
  • Testability: Allows unit testing AdvanceService in isolation by mocking AppDbContext or IAuditService without spinning up a live web server.
  • Maintainability: Changing a rule (e.g., auto-flagging expenses over $200) requires editing only one file (ExpenseService.cs).

3. How it operates in practice:

Blazor UI / MAUI → Sends DTO via HTTP → API Controller → Calls IAdvanceService interface → AdvanceService validates & mutates EF Core Entity → AppDbContext saves to SQL Server → Returns DTO to Client

Below is the exact production-ready C# code structure showing how the Shared interfaces, DTOs, EF Core Entities, Backend Services, and Controllers link together: 

// -------------------------------------------------------------
// 1. SHARED PROJECT (Zillion.PettyCash.Shared)
// -------------------------------------------------------------

// Shared/Enums/AdvanceStatus.cs
public enum AdvanceStatus { Draft = 1, Pending = 2, Approved = 3, Rejected = 4, FundsIssued = 5, Reconciled = 6 }

// Shared/DTOs/AdvanceDtos.cs
public record CreateAdvanceDto(decimal RequestedAmount, string Purpose, string Destination);
public record AdvanceDetailDto(int AdvanceId, int EmployeeId, decimal Amount, AdvanceStatus Status, DateTime RequestedAt);

// Shared/Interfaces/IAdvanceService.cs
public interface IAdvanceService
{
    Task<AdvanceDetailDto> SubmitAdvanceAsync(CreateAdvanceDto dto, int employeeId);
    Task ApproveAdvanceAsync(int advanceId, int approverId, decimal approvedAmount);
}

// -------------------------------------------------------------
// 2. BACKEND SERVER PROJECT (Zillion.PettyCash.Server)
// -------------------------------------------------------------

// Server/Entities/AdvanceRequest.cs (EF Core Entity)
public class AdvanceRequest
{
    public int AdvanceId { get; set; }
    public int EmployeeId { get; set; }
    public decimal RequestedAmount { get; set; }
    public string Purpose { get; set; } = "";
    public AdvanceStatus Status { get; set; } = AdvanceStatus.Pending;
    public DateTime RequestedAt { get; set; } = DateTime.UtcNow;
}

// Server/Services/AdvanceService.cs (Concrete Realization)
public class AdvanceService : IAdvanceService
{
    private readonly AppDbContext _db;
    public AdvanceService(AppDbContext db) => _db = db;

    public async Task<AdvanceDetailDto> SubmitAdvanceAsync(CreateAdvanceDto dto, int employeeId)
    {
        var entity = new AdvanceRequest { EmployeeId = employeeId, RequestedAmount = dto.RequestedAmount, Purpose = dto.Purpose };
        _db.AdvanceRequests.Add(entity);
        await _db.SaveChangesAsync();
        return new AdvanceDetailDto(entity.AdvanceId, entity.EmployeeId, entity.RequestedAmount, entity.Status, entity.RequestedAt);
    }
}

// Server/Controllers/AdvanceController.cs (Lightweight API Endpoint)
[ApiController]
[Route("api/[controller]")]
public class AdvanceController : ControllerBase
{
    private readonly IAdvanceService _service;
    public AdvanceController(IAdvanceService service) => _service = service;

    [HttpPost]
    public async Task<IActionResult> Create(CreateAdvanceDto dto)
    {
        var result = await _service.SubmitAdvanceAsync(dto, User.GetUserId());
        return CreatedAtAction(nameof(GetById), new { id = result.AdvanceId }, result);
    }
}
